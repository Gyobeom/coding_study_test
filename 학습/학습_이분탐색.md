# 학습: 이분탐색 (bisect·파라메트릭 서치)

> 관련 문서: [학습_정렬](학습_정렬.md) · [학습_힙](학습_힙.md) · [학습_그리디](학습_그리디.md) · [학습_BFS](../problems/programmers/lv2/006_게임_맵_최단거리/학습_BFS.md)

[학습_정렬](학습_정렬.md) 1절에서 "정렬해두면 이분탐색으로 O(log n)에 찾는다"고 예고했습니다. 이제 그 **이분탐색(binary search)** 을 정리합니다.
이분탐색은 "값을 빨리 찾는" 도구로 시작하지만, 진짜 힘은 **"답 자체를 이분탐색으로 찾는"**(파라메트릭 서치) 응용에 있습니다.
예제는 전부 중립 소재(숫자·생산량)로 만들었고, 아래 모든 출력값은 실제로 실행해 검증한 값입니다.

---

## 1. 이분탐색이란 — "절반씩 버려 가며 찾는다"

이분탐색은 **정렬된 데이터**에서 찾는 값을 **절반씩 범위를 줄여** 가며 찾는 방법입니다.

- **순차탐색**: 앞에서부터 하나씩 봅니다. 최악엔 전부 봐야 해서 **O(N)**.
- **이분탐색**: 가운데를 보고 "찾는 값이 이보다 큰가 작은가"로 **절반을 통째로 버립니다**. 그래서 **O(log N)**.

정렬돼 있다는 게 왜 결정적일까요? 가운데 값이 목표보다 작으면, **그 왼쪽은 볼 필요도 없이** 전부 목표보다 작다는 걸 알 수 있기 때문입니다. 정렬이 "한쪽을 통째로 버릴 근거"를 줍니다.

| N | 순차탐색 O(N) | 이분탐색 O(log N) |
|---|---|---|
| 1,000 | 최대 1,000번 | 약 10번 |
| 1,000,000 | 최대 100만번 | 약 20번 |
| 1,000,000,000 | 최대 10억번 | 약 30번 |

N이 10억이어도 약 30번이면 찾습니다. "절반씩 버린다"의 위력입니다([학습_정렬](학습_정렬.md) 5절 "비교 한 번에 후보 절반"과 같은 스무고개 감각).

> **한 줄 정리:** 이분탐색은 **정렬된** 데이터에서 가운데를 보고 **절반을 버리기**를 반복해 O(log N)에 찾습니다. 정렬이 "한쪽을 통째로 버릴" 근거를 주기 때문에 성립합니다.

## 2. 기본 형태 — left·right·mid

골격은 항상 같습니다. **범위를 `left`~`right`로 잡고, 가운데 `mid`를 목표와 비교해 한쪽을 버립니다.**

```python
def bsearch(arr, target):
    left, right = 0, len(arr) - 1
    while left <= right:
        mid = (left + right) // 2
        if arr[mid] == target:
            return mid                 # 찾음
        elif arr[mid] < target:
            left = mid + 1             # 목표는 오른쪽에 → 왼쪽 버림
        else:
            right = mid - 1            # 목표는 왼쪽에 → 오른쪽 버림
    return -1                          # 못 찾음

arr = [1, 3, 5, 7, 9, 11]
print(bsearch(arr, 7))   # 3
print(bsearch(arr, 4))   # -1  (없는 값)
```

- `mid`가 목표와 **같으면** 끝.
- `arr[mid]`가 목표보다 **작으면** 목표는 오른쪽 → `left = mid + 1`.
- `arr[mid]`가 목표보다 **크면** 목표는 왼쪽 → `right = mid - 1`.

버린 쪽(`mid` 자신 포함)은 다시 안 봅니다. 매 반복마다 범위가 절반이 됩니다.

### `bisect` 모듈 — 직접 안 짜도 된다

파이썬은 정렬된 리스트용 이분탐색을 **`bisect`** 모듈로 제공합니다. "값을 넣을 위치"를 O(log N)에 찾아 줍니다.

```python
import bisect

xs = [1, 3, 3, 3, 5]
print(bisect.bisect_left(xs, 3))    # 1   ← 3이 들어갈 "가장 왼쪽" 자리
print(bisect.bisect_right(xs, 3))   # 4   ← 3이 들어갈 "가장 오른쪽" 자리
print(bisect.bisect_left(xs, 4))    # 4   ← 없는 값이면 삽입 위치
```

- `bisect_left(a, x)` — `x`를 넣어도 정렬이 유지되는 **가장 왼쪽** 위치. 같은 값이 여럿이면 그 **앞**.
- `bisect_right(a, x)` — 같은 조건의 **가장 오른쪽** 위치. 같은 값들의 **뒤**.

이 둘의 차이로 **"값의 개수"** 를 셀 수 있습니다 — 흔한 관용구입니다.

```python
import bisect

xs = [1, 3, 3, 3, 5]
print(bisect.bisect_right(xs, 3) - bisect.bisect_left(xs, 3))   # 3   (3이 3개)
```

`insort`는 아예 정렬을 유지하며 삽입해 줍니다.

```python
import bisect

ys = [1, 3, 5]
bisect.insort(ys, 4)
print(ys)   # [1, 3, 4, 5]
```

> **한 줄 정리:** 기본 골격은 **`left`/`right`로 범위, `mid`로 비교, 한쪽 버리기**입니다. 정렬된 리스트에서 "위치·개수·존재"만 알면 될 땐 직접 안 짜고 **`bisect_left`/`bisect_right`** 를 쓰면 됩니다.

## 3. "답을 이분탐색" — 파라메트릭 서치

여기가 코테에서 이분탐색이 진짜 무기가 되는 지점입니다. 지금까지는 **"정렬된 배열에서 값을 찾았"** 지만, 파라메트릭 서치는 **"조건을 만족하는 답 자체를 이분탐색으로 찾습니다."**

### 발상의 전환 — 최적화 문제를 "결정 문제"로 바꾼다

"~하는 **최소/최대 값**은?"이라는 최적화 문제를, **"어떤 값 X면 조건을 만족하나? (예/아니오)"** 라는 결정 문제로 바꿉니다. 그리고 그 **X를 이분탐색**합니다.

이게 성립하려면 조건에 **단조성**이 있어야 합니다 — "X가 크면 (혹은 작으면) 항상 조건을 만족하고, 경계를 넘으면 항상 만족 못 한다"는 성질입니다. 그러면 답은 그 **경계**이고, 경계는 이분탐색으로 찾을 수 있습니다.

```
가능 여부:  ✗ ✗ ✗ ✗ | ✓ ✓ ✓ ✓ ✓
                     ↑
                  이 경계(가장 왼쪽 ✓)가 답
```

### 중립 예제 — "N일 안에 다 만들려면 하루 최소 생산량은?"

주문 여러 개가 있고, 한 라인이 하루에 `speed`개까지 만듭니다. 주문 하나를 만드는 데 `ceil(주문크기 / speed)`일이 걸립니다. **총 D일 안에 다 만들려면 `speed`의 최솟값은?**

- `speed`가 **크면** 빨리 만드니 D일 안에 됩니다(조건 만족 ✓).
- `speed`가 **작으면** 오래 걸려 D일을 넘깁니다(조건 불만족 ✗).

즉 `speed`에 **단조성**이 있습니다. "D일 안에 되나?"를 판정하는 함수를 만들고, 그걸 만족하는 **가장 작은 `speed`** 를 이분탐색합니다.

```python
import math

def days_needed(orders, speed):                     # speed로 만들 때 걸리는 총 일수
    return sum(math.ceil(o / speed) for o in orders)

def min_speed(orders, D):
    left, right = 1, max(orders)                    # speed 후보 범위
    ans = right
    while left <= right:
        mid = (left + right) // 2
        if days_needed(orders, mid) <= D:           # 이 speed면 D일 안에 됨 → 더 줄여보자
            ans = mid
            right = mid - 1
        else:                                       # 너무 느림 → speed 키워야
            left = mid + 1
    return ans

orders = [10, 20, 30]
print(min_speed(orders, 6))       # 10
print(days_needed(orders, 10))    # 6   (1+2+3 = 6일, D=6에 딱)
print(days_needed(orders, 9))     # 9   (2+3+4 = 9일, D=6 초과 → 불가)
```

핵심은 **탐색 대상이 배열이 아니라 "답의 후보 범위(`speed` 1~max)"** 라는 점입니다. 배열에서 값을 찾는 게 아니라, **답이 될 수 있는 숫자 범위**를 이분탐색합니다. "되면 더 줄여보고(`right`), 안 되면 키운다(`left`)" — 정답 경계로 좁혀 갑니다.

> **한 줄 정리:** "~하는 **최소/최대**는?" 문제에서 **답 후보에 단조성**("이 값이면 되고, 더 작으면(크면) 안 된다")이 보이면, 답 범위를 **이분탐색**합니다. 값을 찾는 게 아니라 **답 자체를 찾는** 것 — 이게 코테 이분탐색의 핵심 응용입니다.

## 4. 경계 처리 주의 — 무한루프 함정

이분탐색은 골격이 단순한 대신 **경계 조건에서 실수가 잦습니다.** 특히 무한루프에 빠지기 쉽습니다.

### `while left <= right` vs `while left < right`

- **`<=`** (2·3절에서 쓴 형태): 범위가 `[left, right]`로 **양 끝을 다 포함**합니다. `left == right`인 원소 하나짜리 범위도 검사하고 끝냅니다. "특정 값을 찾아 인덱스를 반환"하는 기본형에 잘 맞습니다.
- **`<`**: 범위가 `[left, right)`로 **오른쪽을 안 포함**합니다. `left == right`가 되면 루프를 끝내고, 그 `left`가 답 위치가 됩니다. `bisect` 계열의 "경계 위치 찾기"에 많이 씁니다.

둘 다 옳지만, **범위를 좁힐 때(`left`/`right` 갱신)와 짝이 맞아야** 합니다. 짝이 어긋나면 검사해야 할 원소를 건너뛰거나, 범위가 안 줄어 무한루프가 됩니다.

### 무한루프는 왜 생기나 — "범위가 안 줄어드는" 순간

무한루프의 원인은 거의 항상 **"매 반복마다 범위가 반드시 줄어드는가?"** 가 깨질 때입니다.

- `mid = (left + right) // 2`는 **버림 나눗셈**이라 `mid`가 `left` 쪽으로 치우칩니다. 그래서 `left = mid`(mid+1이 아니라)로 갱신하면, `left`와 `right`가 붙었을 때 `mid`가 계속 `left`가 되어 **영원히 안 줄어듭니다.**
- 기본형(`<=`)에서 `left = mid + 1`, `right = mid - 1`처럼 **항상 `mid`를 건너뛰어** 갱신하면 범위가 최소 1씩 줄어 안전합니다. `mid`는 이미 검사했으니 다시 볼 이유도 없습니다.

> **한 줄 정리:** `<=`는 양 끝 포함(기본형), `<`는 오른쪽 열림(경계 찾기)이고, **갱신식과 짝이 맞아야** 합니다. 무한루프가 의심되면 **"매 반복마다 범위가 정말 줄어드는가?"** 와 **"`mid`를 건너뛰어 갱신했는가(`mid±1`)?"** 를 점검하세요. 헷갈리면 **`bisect` 모듈**을 쓰는 게 가장 안전합니다.

3. 파라메트릭 서치란 무엇을 무엇으로 바꾸는 것인가? 이 방법이 성립하려면 답 후보에 어떤 성질(단조성)이 있어야 하는가?
