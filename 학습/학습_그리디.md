# 학습: 그리디 (탐욕법)

> 관련 문서: [학습_정렬](학습_정렬.md) · [학습_DFS](학습_DFS.md) · [학습_해시](학습_해시.md) · [학습_BFS](../problems/programmers/lv2/006_게임_맵_최단거리/학습_BFS.md)

지금까지는 DFS·BFS로 **모든 경우를 빠짐없이** 훑고, 해시·정렬로 그 훑기를 빠르게 만들었습니다.
이 문서에서 **그리디(탐욕법)** 를 정리합니다. 그리디는 DFS와 정반대의 태도입니다 — 모든 경우를 보지 않고, **매 순간 가장 좋아 보이는 하나만 집고 앞으로만** 갑니다.
예제는 전부 중립 소재(회의·짐·동전·숫자)로 만들었고, 아래 모든 출력값은 실제로 실행해 검증한 값입니다.

---

## 1. 그리디란 무엇인가 — "지금 제일 좋아 보이는 것을 집고 되돌아보지 않는다"

그리디는 **매 순간 가장 좋아 보이는 선택을 하고, 한 번 고른 것은 되돌아보지 않는** 방식입니다.
"전체를 놓고 최선을 계산"하는 게 아니라, **눈앞의 한 걸음마다 그때 최선**을 집고 나아갑니다.

### 완전탐색(DFS)과의 대비

같은 "최적을 찾는다"는 목표라도, **어디까지 보느냐**가 정반대입니다. ([학습_DFS](학습_DFS.md) 참고)

| | 완전탐색 (DFS) | 그리디 |
|---|---|---|
| 한 마디로 | **모든 경우**를 다 열어 보고 그중 최선을 고름 | 매 순간 **지금 최선**만 집고 앞으로만 감 |
| 되돌아봄 | 있음 (막히면 back, 다른 갈래 시도) | **없음** (한 번 고르면 끝) |
| 보는 범위 | 전역 (모든 갈래) | 지역 (눈앞 한 수) |
| 비용 | 갈래가 많으면 폭발($2^n$ 등) | 대개 정렬 한 번 + 한 번 훑기 |

- 완전탐색은 "가능한 조합을 전부 만들어 놓고 그중 최선"이라, 갈래가 많으면 $2^n$·$n!$ 로 폭발합니다.
- 그리디는 "각 단계에서 최선 하나"만 고르니 대개 **한 번 훑는 것으로 끝**나 훨씬 빠릅니다.

문제는, **눈앞의 최선을 쌓은 것이 정말 전체의 최선이냐**는 것입니다. 그게 보장될 때만 그리디가 옳습니다(2절).

> **한 줄 정리:** 완전탐색이 "모든 길을 다 걸어 보고 고르는" 것이라면, 그리디는 "갈림길마다 좋아 보이는 쪽으로만 걷고 뒤돌아보지 않는" 것입니다. 빠른 대신, **되돌아보지 않아도 되는 문제**에서만 옳습니다.

## 2. 그리디가 성립하는 조건 — "지역 최적의 누적이 전역 최적인가?"

그리디의 전부이자 가장 큰 함정이 여기 있습니다. 반드시 스스로 물어야 합니다.

> **"매 단계 최선을 집어 쌓은 결과가, 정말 전체의 최선과 같은가?"**

이게 참이면 그리디는 O(N log N)급으로 빠르게 정답을 냅니다. 그런데 **거짓인데 그리디를 쓰면, 코드는 멀쩡히 돌아가면서 틀린 답을 냅니다.** 이게 무서운 점입니다 — 에러가 안 나고 "그럴듯한 오답"이 나옵니다.

### 왜 의심이 반드시 필요한가

정렬이나 DFS는 "맞게 짰으면 맞는 답"이 나옵니다. 그런데 그리디는 **전략 자체가 그 문제에 맞아야** 맞는 답이 나옵니다. 코드가 맞아도 전략이 안 맞으면 틀립니다.

- **성립하면**: 매 단계 최선을 집기만 하면 되니 대개 "정렬 → 순서대로 한 번 훑기"로 끝나 O(N log N).
- **성립 안 하면**: 지금 최선이 나중에 발목을 잡아, 눈앞엔 이득이지만 전체로는 손해가 됩니다(5절 반례).

그래서 그리디를 떠올렸다면, **곧바로 코드를 짜지 말고** "이 전략의 반례를 만들 수 있나?"를 먼저 시도해 봐야 합니다. 작은 반례가 안 만들어지면 그때 믿고 짭니다.

> **한 줄 정리:** 그리디의 승부는 코드가 아니라 **"지역 최적의 누적 = 전역 최적"이 성립하는지의 증명(또는 반례 탐색)** 에서 납니다. 이 질문을 건너뛰면, 돌아가지만 틀린 코드를 만들게 됩니다.

## 3. 자주 쓰는 그리디 패턴 세 가지

성립이 확인됐다고 치고, 실제로 그리디가 취하는 모양은 대개 아래 셋 중 하나입니다. 공통점은 **거의 항상 정렬로 시작**한다는 것입니다([학습_정렬](학습_정렬.md) 1절 "정렬해두면 그다음이 쉽다"의 대표 사례).

### ⓐ 정렬 후 순서대로 선택 (구간·크기 기준)

"기준 하나로 줄 세운 뒤, 앞에서부터 조건에 맞는 것만 집는다". 아래는 시간이 겹치지 않게 회의를 **최대한 많이** 넣는 예입니다. **끝나는 시각이 이른 것부터** 고르는 게 핵심입니다.

```python
meetings = [(1, 3), (2, 5), (4, 6), (0, 2)]
meetings.sort(key=lambda x: x[1])   # 끝나는 시각 기준 정렬
end = 0
picked = []
for s, e in meetings:
    if s >= end:          # 앞 회의가 끝난 뒤 시작하면 선택
        picked.append((s, e))
        end = e
print(picked)             # [(0, 2), (2, 5)]
```

"빨리 끝나는 것부터"라는 지역 최선을 순서대로 집었을 뿐인데, 담을 수 있는 최대 개수가 나옵니다. **무엇을 기준으로 정렬하느냐**가 곧 전략입니다.

### ⓑ 큰 것부터 / 작은 것부터 짝짓기

"극단(가장 큰 것/작은 것)부터 처리한다". 아래는 무거운 짐부터 꺼내 놓는 예입니다.

```python
weights = sorted([7, 3, 8, 2], reverse=True)  # 무거운 것부터
print(weights)                                # [8, 7, 3, 2]
```

무거운 것부터 처리하면 "가장 다루기 까다로운 것을 먼저 짝지어 놓는" 전략이 됩니다. 이때 흔히 **정렬된 리스트의 양 끝(가장 큰 것 ↔ 가장 작은 것)에서 인덱스 두 개로 좁혀 오는** 투 포인터와 결합합니다([학습_정렬](학습_정렬.md) 4절의 "양 끝에서 훑기").

### ⓒ 교환하며 확인

"지금 놓인 것과 바꾸면 더 좋아지나?"를 따져 더 좋을 때만 취한다. 아래는 자릿수를 재배열해 **가장 큰 수**를 만드는 감각의 예입니다.

```python
s = "394"
best = "".join(sorted(list(s), reverse=True))
print(best)   # 943
```

여기선 정렬로 한 번에 처리했지만, 일반적으로는 "앞자리에 더 큰 숫자를 놓을 수 있으면 바꾼다"처럼 **바꿔서 이득이면 바꾸는** 판단이 반복됩니다.

> **공통 감각:** 세 패턴 모두 **"먼저 줄을 세우고(정렬), 앞에서부터 지역 최선을 취한다"** 로 요약됩니다. 그리디 문제에서 막히면 "무엇을 기준으로 정렬하면 앞에서부터 집기만 하면 될까?"를 먼저 물어보세요.

## 4. 그리디 vs 완전탐색 — 언제 무엇을 쓰나

같은 최적화 문제라도 **입력 규모**가 선택을 가릅니다. 판단 기준은 [학습_BFS](../problems/programmers/lv2/006_게임_맵_최단거리/학습_BFS.md) 6절에서 익힌 **(처리 횟수) × (1회 비용)** 그대로입니다.

| 상황 | 고를 도구 | 이유 |
|---|---|---|
| N이 **작다** (대략 ~20 이하, 조합·순열을 다 봐도 됨) | **완전탐색(DFS)** | $2^n$·$n!$ 이 감당 가능. 모든 경우를 봐 **확실히** 최선을 고름 |
| N이 **크다** (수천~수십만) | **그리디** | 완전탐색은 폭발. 정렬 O(N log N) + 훑기 O(N)로 끝남 |
| 성립 조건이 **의심스럽다** | **완전탐색 우선** | 그리디가 틀릴 위험. 규모가 되면 확실한 완전탐색이 안전 |

- **완전탐색**: $2^n$ 은 n=20이면 약 100만이라 아직 괜찮지만, n=30이면 약 10억으로 시간 초과입니다. 그래서 "모든 조합을 본다"는 **N이 작을 때만** 쓸 수 있습니다.
- **그리디**: 정렬이 지배적이라 O(N log N). N=100,000이어도 약 170만 번([학습_정렬](학습_정렬.md) 5절 표)이라 여유입니다.

> **판단 순서:** ① 제약 조건에서 N을 확인한다 → ② N이 작아 모든 경우를 봐도 되면 **완전탐색이 안전**(반례 걱정 없음) → ③ N이 커서 완전탐색이 폭발하면 **그리디를 시도하되, 반드시 성립 조건(2절)을 먼저 의심**한다.

## 5. "그리디가 안 되는" 반례 감각

2절에서 말한 "성립 안 하면 틀린다"를 눈으로 봅니다. 가장 유명한 예가 **동전(거스름돈) 문제**입니다.

### 그리디가 되는 경우 — 배수 체계 동전

동전 종류가 서로 **배수 관계**(예: 500, 100, 50, 10 — 큰 것이 작은 것들로 딱 나뉨)이면, "큰 동전부터 최대한" 그리디가 **항상** 최소 개수를 줍니다.

```python
coins = [500, 100, 50, 10]
amount = 1260
cnt = 0
for c in coins:
    cnt += amount // c
    amount %= c
print(cnt, amount)   # 6 0   (500×2 + 100×2 + 50×1 + 10×1 = 6개, 남은 0원)
```

큰 것부터 집어도 손해가 없습니다 — 큰 동전이 작은 동전들의 배수라, 나중에 쪼갤 필요가 안 생기기 때문입니다.

### 그리디가 틀리는 경우 — 배수가 아닌 동전

그런데 동전이 `[1, 3, 4]` 처럼 **배수 관계가 아니면** 큰 것부터 그리디가 **틀립니다.** 6원을 만들어 봅니다.

```python
coins2 = sorted([1, 3, 4], reverse=True)   # [4, 3, 1]
amount2 = 6
greedy_cnt, a = 0, amount2
for c in coins2:
    greedy_cnt += a // c
    a %= c
print("그리디:", greedy_cnt)   # 그리디: 3   (4 + 1 + 1 = 세 개)
```

그리디는 "큰 4부터"라며 `4 + 1 + 1 = 3개`를 씁니다. 하지만 실제 최소는 **`3 + 3 = 2개`** 입니다. 완전탐색으로 확인하면:

```
동전 [4,3,1]로 6원 만들기
  그리디: 4 → 남은 2 → 1+1  ⟹ 3개
  최적  : 3 → 남은 3 → 3    ⟹ 2개   ← 더 적다!
```

**눈앞의 최선(가장 큰 4를 집기)이 전체의 최선을 망친** 것입니다. 4를 집는 순간 남은 2원을 1원 두 개로밖에 못 채우게 됩니다. 3을 두 번 쓰는 길은 "지금 최선"이 아니라서 그리디는 **아예 쳐다보지 않습니다.**

> **반례 감각:** "큰 것부터 집으면 되겠지"가 통하려면 **큰 것을 집어도 나중에 손해가 없어야** 합니다. 동전이 배수 관계면 그 보장이 있고, 아니면 깨집니다.
> 그리디 전략이 떠오르면 이렇게 자문하세요 — **"지금 최선을 집었을 때, 그게 나중 선택을 망치는 작은 반례를 만들 수 있나?"** 만들어지면 그리디는 틀린 것이고, 규모가 되면 완전탐색으로 돌아갑니다(4절).

## 6. 자기 점검 체크리스트 (문서 닫기 전 스스로 답해보기)

1. 그리디와 완전탐색(DFS)은 "보는 범위"와 "되돌아봄" 면에서 각각 어떻게 다른가? 그리디가 완전탐색보다 빠른 근본 이유는 무엇인가?
2. 그리디를 쓰기 전에 **반드시 던져야 하는 한 가지 질문**은 무엇인가? 그 질문이 거짓일 때, 정렬·DFS와 달리 그리디는 왜 "돌아가지만 틀린" 위험이 있는가?
3. "정렬 후 순서대로 선택" 패턴에서, 회의를 최대한 많이 넣으려면 **무엇을 기준으로** 정렬해야 하는가? 왜 그 기준인가?
4. 같은 최적화 문제에서 N이 작을 때와 클 때 완전탐색·그리디 중 무엇을 먼저 떠올리는가? 그 경계를 $2^n$ 의 크기로 설명해 보라.
5. 동전 `[1, 3, 4]`로 6원을 만들 때 큰 것부터 그리디가 왜 틀리는가? "지금 최선이 나중을 망친다"를 이 예로 설명해 보라.
