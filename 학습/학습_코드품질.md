# 학습: 코드 품질 (읽기 좋은 코드 습관)

> 관련 문서: [학습_해시](학습_해시.md) · [학습_정렬](학습_정렬.md) · [학습_그리디](학습_그리디.md) · [학습_스택_큐](학습_스택_큐.md)

지금까지는 "**어떻게 풀까**"(DFS·BFS·해시·정렬·그리디)를 익혔습니다. 이 문서는 방향이 다릅니다 — **"어떻게 쓸까"**, 즉 정답을 넘어 **읽기 좋은 코드**를 쓰는 습관을 정리합니다.
이 저장소에서 실제로 지적받았던 리뷰 포인트(의미 없는 이름, 스테일 주석, 남은 디버그 `print`, 리스트 `in`의 숨은 O(N) 등)를 한자리에 모은 것입니다. 예제는 전부 중립 소재(과일·점수·시간 등)이고, 아래 출력값은 실제로 실행해 검증했습니다.

**이 문서 사용법:** 외우는 문서가 아닙니다. 문제를 풀고 **제출 직전** 6절 체크리스트를 훑다가 걸리는 항목이 있으면 해당 절로 돌아오는 식으로 씁니다.

---

## 1. 왜 코드 품질인가 — 정답 ≠ 좋은 코드

테스트를 다 통과했는데도 "이건 좋은 코드가 아니다"라고 말할 수 있습니다. **정답과 품질은 다른 축**이기 때문입니다.

- **빅테크 코테는 코드 품질도 평가합니다.** 온사이트·라이브 코딩에서는 사람이 코드를 읽습니다. 같은 정답이라도 **네이밍·구조·관용구**에서 "협업 가능한가"를 봅니다. 통과했어도 `a`, `tmp`, `data2`가 난무하면 감점 요인입니다.
- **실무의 코드는 쓰는 시간보다 읽는 시간이 훨씬 깁니다.** 몇 달 뒤의 내가·동료가 계속 읽고 고칩니다. "5분 아끼려 줄인 이름"이 나중에 "이게 뭐였지"로 30분을 잡아먹습니다.

핵심 한 줄: **코드는 컴퓨터가 실행하려고가 아니라 사람이 읽으려고 쓴다.** 아래 2~5절은 이를 네 방향(이름·주석·자료구조·구조)으로 구체화합니다.

## 2. 네이밍 — 이름이 곧 문서다

이름은 **가장 값싼 주석**입니다. 잘 지은 이름 하나가 주석 세 줄을 없앱니다.

### ⓐ 의미 없는 접두사(`new_`/`temp_`/`data`/`arr`) 금지 — 의도를 담는다

`new_`, `temp_`, `data`, `arr`, `list1` 같은 이름은 **"무엇인지"를 하나도 말해주지 않습니다.** 변수의 **역할**을 이름에 담으세요.

```python
# before — 무엇을 담는지 이름만으론 알 수 없다
new_arr = []
for x in prices:
    new_arr.append(x * 2)

# after — "가격을 2배 한 것들"이라고 이름이 말해준다
doubled_prices = [price * 2 for price in prices]
```

`new_arr`는 "새 배열"이라는 말만 하지만, `doubled_prices`는 코드를 읽기 전에 내용을 알려줍니다. "필요한 체육복 수"라면 `need_uniform`, "빌려줄 수 있는 사람들"이라면 `lenders`처럼 **도메인 단어**를 이름에 넣는 게 목표입니다.

### ⓑ 축약어 지양 — `cnt` → `count`

타이핑 몇 글자 아끼려고 모음을 빼지 마세요. `cnt`, `idx`, `res`, `val`, `lst`는 읽는 사람에게 **해독 부담**을 지웁니다. `cnt→count`, `res→result`, `idx→index`, `tmp→역할을 담은 이름`.
예외: 반복문의 `i`, `j`, 좌표 `x`, `y`처럼 **관례가 굳어진 짧은 이름**은 그대로 써도 됩니다. 자작 축약만 피하면 됩니다.

### ⓒ 불리언은 `is_`/`has_`로

불리언 변수·함수에 `is_`, `has_`, `can_` 접두사를 붙이면 **읽을 때 참/거짓 판정임이 바로** 보입니다.

```python
def is_even(n):
    return n % 2 == 0

print([is_even(n) for n in [1, 2, 3, 4]])   # [False, True, False, True]
```

`even(n)`보다 `is_even(n)`이 `if is_even(x):`로 읽으면 문장처럼 자연스럽습니다. `has_visited`, `can_move`도 마찬가지입니다.

### ⓓ 컬렉션은 복수형으로

여러 개를 담는 리스트·집합·딕셔너리는 **복수형**으로. `name`은 하나, `names`는 여럿임을 이름만으로 구분합니다.

```python
names = ["김", "이", "박"]
for name in names:      # 복수(names)에서 단수(name)를 꺼낸다 — 읽기 자연스럽다
    ...
```

`for x in list1`보다 `for name in names`가 반복 변수의 정체까지 알려줍니다.

### ⓔ 파이썬 관례 — `snake_case`

파이썬 변수·함수는 `snake_case`가 표준입니다. `camelCase`나 `PascalCase`는 파이썬에서 이질적입니다. 클래스명만 `PascalCase`, 상수는 `UPPER_SNAKE_CASE`(5절 ⓑ)입니다.

> **네이밍 감각:** 이름을 지을 때 "**이 변수를 모르는 사람이 이름만 보고 내용을 짐작할 수 있나?**"를 물어보세요. 짐작이 안 되면 아직 덜 지은 이름입니다.

## 3. 주석 — "왜"만 남기고 "무엇"은 코드로

주석은 많을수록 좋은 게 아닙니다. **틀린 주석은 없느니만 못합니다.**

### ⓐ 스테일(stale) 주석의 해악 — 코드는 바뀌는데 주석은 안 바뀐다

가장 위험한 주석은 **코드와 어긋난 주석**입니다. 코드를 고칠 때 주석을 함께 안 고치면, 주석이 **거짓말**을 하게 됩니다.

```python
# ⚠️ 코드는 set인데 주석은 "배열"이라 말한다 — 읽는 사람을 속인다
seen = set()          # 방문한 노드를 담는 배열   ← 거짓: 이건 집합(set)이다
```

읽는 사람은 주석을 믿고 "배열이니 `in`이 O(N)이겠구나"라 오해합니다. **주석이 코드보다 오래되면 버그의 원인**이 됩니다. 코드를 고치면 주석도 함께 고치거나 **아예 지우세요.**

### ⓑ "무엇"이 아니라 "왜"를 적는다

코드를 읽으면 알 수 있는 "무엇"은 주석으로 반복하지 마세요. 코드만 봐선 알 수 없는 "**왜**"만 남깁니다.

```python
# 나쁜 주석 — 코드를 그대로 옮겼을 뿐 (무엇)
count = count + 1     # count를 1 증가시킨다

# 좋은 주석 — 코드에 안 드러난 이유 (왜)
count = count + 1     # 0-based 인덱스라 화면 표시용으로 1을 더한다
```

앞은 코드를 읽으면 아는 걸 반복해 눈만 어지럽히고, 뒤는 "왜 하필 +1인가"라는 코드만 봐선 모르는 맥락을 줍니다.

### ⓒ 자기설명적 코드가 주석보다 낫다

주석으로 설명하고 싶어지면, 먼저 **코드 자체를 설명적으로 바꿀 수 없나** 생각하세요. 이름·함수로 풀면 주석이 필요 없습니다.

```python
# before — 주석으로 의미를 설명
d = s / 3600          # 초를 시간으로 변환

# after — 이름이 스스로 설명하니 주석이 필요 없다
hours = seconds / SECONDS_PER_HOUR
```

주석은 코드가 바뀌면 썩지만(ⓐ), **이름은 코드의 일부라 같이 유지**됩니다. 그래서 "좋은 이름 > 주석"입니다.

### ⓓ 죽은 코드·디버그 `print`는 제출 전에 지운다

풀다가 남긴 **디버그 `print`**, 주석 처리해 둔 **죽은 코드**는 제출 전에 반드시 치웁니다. 남아 있으면 지저분할 뿐 아니라, 채점에서 불필요한 출력으로 **오답 처리**될 수도 있습니다.

```python
# before — 디버그 흔적이 남아 있다
def total(items):
    s = 0
    for it in items:
        s += it
    # print("debug", s)    ← 지워야 할 디버그
    # s = s * 2            ← 죽은 코드 (한때 시도했던 것)
    return s

# after — 군더더기 없이 깔끔
def total(items):
    return sum(items)      # 6  (items=[1,2,3])
```

> **주석 감각:** 주석을 쓰기 전에 "이건 코드/이름으로 풀 수 있나?"를 먼저 묻고, 남길 거면 "왜"만 남기세요. 그리고 **제출 전 디버그 `print`와 죽은 코드는 반드시 청소**합니다.

## 4. 자료구조·함수 선택 — 용도에 맞게 고른다

같은 결과라도 **어떤 자료구조·함수를 쓰느냐**가 속도와 가독성을 가릅니다. 특히 **숨은 복잡도**를 의식하는 게 이 절의 핵심입니다.

### ⓐ list vs set vs dict — 멤버십 검사는 set

"이게 안에 있나?"(멤버십)를 반복 확인한다면 **리스트가 아니라 `set`** 입니다. 리스트 `in`은 처음부터 훑어 **O(N)**, `set`·`dict`의 `in`은 **O(1)** 입니다.

```python
seen_list = ["a", "b", "c"]
seen_set = {"a", "b", "c"}
print("b" in seen_list, "b" in seen_set)   # True True   ← 결과는 같지만
print("z" in seen_list, "z" in seen_set)   # False False  ← set이 훨씬 빠르다
```

결과는 같아서 작은 입력에선 티가 안 나지만, 반복문 안에서 리스트 `in`을 돌리면 전체가 **O(N²)** 로 뛰어 시간 초과가 납니다([학습_해시](학습_해시.md) 5·6절). 고르는 기준: **순서·중복이 필요하면 list, "있나 없나"만 보면 set, 키→값이면 dict.**

### ⓑ 파이썬 관용구 — `enumerate`/`zip`/컴프리헨션/`Counter`/`defaultdict`

파이썬에는 흔한 패턴을 짧고 명확하게 쓰는 관용구가 있습니다. 손으로 인덱스를 굴리는 대신 이걸 쓰면 **버그도 줄고 읽기도 쉽습니다.**

```python
from collections import Counter, defaultdict

# enumerate — 인덱스 변수를 손으로 관리하지 않는다
fruits = ["사과", "배", "감"]
print(list(enumerate(fruits)))     # [(0, '사과'), (1, '배'), (2, '감')]

# Counter — 개수 세기 (get(k,0)+1 관용구의 축약)
print(dict(Counter(["a", "b", "a", "c", "a"])))   # {'a': 3, 'b': 1, 'c': 1}

# defaultdict — 그룹 묶기 (setdefault 없이)
groups = defaultdict(list)
for key, value in [("x", 1), ("y", 2), ("x", 3)]:
    groups[key].append(value)
print(dict(groups))                # {'x': [1, 3], 'y': [2]}
```

`i = 0; ...; i += 1` 대신 `enumerate`, 두 리스트를 인덱스로 짝짓는 대신 `zip`, 개수 세기는 `Counter`. 이 관용구들은 "파이썬을 아는 사람"의 신호이기도 합니다(원리는 [학습_해시](학습_해시.md) 3·4절).

### ⓒ 안전한 함수 — `remove` vs `discard`, `[]` vs `get`

없는 값을 다룰 때 **예외로 멈추는 함수**와 **조용히 넘어가는 함수**를 구분해 쓰세요.

```python
s = {1, 2, 3}
s.discard(9)          # 없어도 조용히 넘어간다 → {1, 2, 3}
# s.remove(9)         # 없으면 KeyError로 멈춘다!

d = {"a": 1}
print(d.get("z", 0))  # 0    ← 없어도 기본값. d["z"]였다면 KeyError
```

- **`set.remove(x)`** / **`dict[k]`** — 없으면 `KeyError`. "반드시 있다"고 확신할 때만.
- **`set.discard(x)`** / **`dict.get(k, 기본값)`** — 없어도 안전. "있을 수도 없을 수도"면 이쪽.

"값이 없을 수 있다"면 안전한 쪽(`discard`/`get`)을 기본으로 삼으세요. 불필요한 `try/except`를 줄여 줍니다.

### ⓓ 숨은 복잡도를 의식한다

`in`, `remove`, `del list[0]`처럼 **한 줄이지만 O(N)** 인 연산이 있습니다. 짧다고 값싼 게 아닙니다.

| 연산 | 겉보기 | 실제 |
|---|---|---|
| `x in list` | 한 줄 | **O(N)** (앞에서 훑음) |
| `list.remove(x)` | 한 줄 | **O(N)** (찾아서 당김) |
| `x in set` / `x in dict` | 한 줄 | **O(1)** |
| `list.pop(0)` | 한 줄 | **O(N)** (앞을 빼면 전부 당김 → [학습_스택_큐](학습_스택_큐.md)의 `deque`) |

> **선택 감각:** "이 한 줄이 반복문 안에서 O(N)이 아닌가?"를 의심하세요. 멤버십은 `set`, 큐는 `deque`, 개수 세기는 `Counter` — **용도에 맞는 도구**를 고르는 게 가독성과 속도를 동시에 잡습니다.

## 5. 구조·가독성 — 중첩을 줄이고 흐름을 곧게

같은 로직도 **구조**에 따라 읽기 난이도가 크게 달라집니다.

### ⓐ 조기 반환(early return)으로 중첩 줄이기

`if` 안에 `if`가 겹겹이 쌓이면 읽기 어렵습니다. **예외·종료 조건을 먼저 처리하고 빠져나오면** 본류 로직이 평평해집니다.

```python
# before — 중첩이 깊다
def classify(n):
    if n > 0:
        if n % 2 == 0:
            return "양수-짝"
        else:
            return "양수-홀"
    else:
        return "음수이하"

# after — 종료 조건을 먼저 반환하고 본류를 평평하게
def classify(n):
    if n <= 0:
        return "음수이하"
    if n % 2 == 0:
        return "양수-짝"
    return "양수-홀"
```

두 함수의 결과는 같습니다(`-3→음수이하, 0→음수이하, 2→양수-짝, 5→양수-홀`). 하지만 after는 `else` 계단이 사라져 **한 줄씩 순서대로** 읽힙니다.

### ⓑ 매직 넘버에 이름 붙이기

코드에 갑자기 튀어나오는 숫자(`3600`, `0.5`, `10000`)를 **매직 넘버**라 합니다. 상수로 이름을 붙이면 의미가 드러나고, 값 변경 시 한 곳만 고치면 됩니다.

```python
# before — 3600이 무슨 수인지 알 수 없다
hours = seconds / 3600

# after — 이름이 의미를 말한다
SECONDS_PER_HOUR = 3600
hours = seconds / SECONDS_PER_HOUR    # 7200 → 2.0
```

상수 이름은 `UPPER_SNAKE_CASE`가 파이썬 관례입니다. 단, 반복문의 `range(1, n)`의 `1`처럼 **자명한 숫자**까지 상수로 뺄 필요는 없습니다.

### ⓒ 함수는 한 가지 일만

한 함수가 입력 파싱·계산·출력까지 다 하면 읽기도 테스트도 어렵습니다. **한 함수는 한 가지 일**을 하게 나누면 이름만 보고 무슨 일을 하는지 압니다. 코테에서 `solution` 하나로 끝내는 경우가 많지만, 로직이 길어지면 `is_valid(...)`, `build_graph(...)`처럼 **의미 단위 헬퍼**로 쪼개는 편이 낫습니다.

### ⓓ 일관성 — 한 파일 안에서 스타일을 통일

한 파일에서 어떤 곳은 `zip`, 어떤 곳은 인덱스; 어떤 이름은 축약, 어떤 이름은 풀어쓰기 — 이렇게 섞이면 읽는 사람이 매번 새로 적응해야 합니다. **완벽한 스타일보다 일관된 스타일**이 낫습니다.

```python
# zip으로 같은 자리끼리 묶는다 — 파일 전체에서 이 방식으로 통일
names = ["김", "이"]
scores = [90, 80]
print(list(zip(names, scores)))    # [('김', 90), ('이', 80)]
```

> **구조 감각:** 들여쓰기가 3단 이상 깊어지면 조기 반환을 의심하고, 정체불명의 숫자가 보이면 이름을 붙이고, 한 함수가 너무 길면 쪼갤 수 있나 보세요. 그리고 무엇을 고르든 **파일 안에서는 일관되게** 씁니다.

## 6. 코테 제출 전 체크리스트 — 시간 압박 속의 균형

시험장에서 품질에 무한정 시간을 쓸 순 없습니다. 하지만 **제출 직전 1~2분**의 점검은 감점을 크게 줄여 줍니다. 아래를 훑으세요.

- [ ] **디버그 `print`·죽은 코드**를 전부 지웠는가? (3절 ⓓ) — 오답 위험까지 있으니 최우선.
- [ ] **이름**이 `a`, `tmp`, `data`, `arr`처럼 의미 없지 않은가? 역할을 담았는가? (2절)
- [ ] **엣지 케이스**(빈 입력·경계값·중복·최대 규모)를 한 번 머릿속으로 넣어봤는가?
- [ ] 반복문 안에서 **리스트 `in`/`remove`**로 숨은 O(N²)을 만들고 있지 않은가? (4절 ⓐⓓ)
- [ ] **스테일 주석**은 없는가? 남긴 주석은 "무엇"이 아니라 "왜"인가? (3절 ⓐⓑ)
- [ ] `return` 해야 할 자리에서 `print`로 끝내지 않았는가? (채점기는 반환값을 비교합니다.)

균형 원칙: **정확성·엣지 > 이름·구조 > 관용구 세련됨** 순으로 시간을 배분하세요. 시간이 빠듯하면 위 3개(디버그 청소·이름·엣지)만이라도 반드시 챙깁니다.

## 7. 실무로의 연결 — 이 습관이 왜 오래 남는가

위 습관들은 코테 감점을 막는 데 그치지 않고 **실무에서 훨씬 크게** 작동합니다.

- **코드 리뷰:** 내 코드는 반드시 동료의 리뷰를 거칩니다. 좋은 이름·평평한 구조는 리뷰어의 시간을 아낍니다. `tmp2`, `data3`이 가득하면 리뷰에서 그대로 지적됩니다 — 코테 감점과 같은 이유입니다.
- **유지보수:** 몇 달 뒤 버그를 고치러 왔을 때 스테일 주석 하나가 잘못된 방향으로 몇 시간을 쓰게 합니다. "왜"만 남긴 주석과 의도 담긴 이름은 **미래의 나에게 주는 선물**입니다.
- **협업:** 일관된 스타일은 팀 코드를 "한 사람이 쓴 것처럼" 만들어, 누가 어느 파일을 열어도 헤매지 않게 합니다.

코테의 품질 점검은 실무 습관의 **축소판 연습**입니다. 지금 들이는 습관이 그대로 현업의 기본기가 됩니다.
